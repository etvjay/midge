## Executive summary

- **Two Separate Connections**: ahujasid's integration uses a Blender add-on socket, normally **localhost:9876**, plus an MCP process launched with `uvx blender-mcp`. It is not a feature built into Blender -> configure both components. [executive_summary[0]] [12]
- **Background Mode Is Not Supported Upstream**: merged PR #272 explicitly rejects `blender -b`; the earlier failure could leave commands waiting **180 seconds** -> use GUI Blender under a virtual display, a different MCP implementation, or ordinary batch scripts. [executive_summary[1]] [18]

- **Export Animation, Not Blender's Entire Runtime**: Blender 4.5/5.0 export object transforms, bones and shape-key values; other animation properties are ignored -> bake procedural behavior into supported channels or recreate it in JavaScript. [executive_summary[5]] [17][executive_summary[6]] [11]
- **Compress Geometry And Textures Separately**: Meshopt covers geometry, morph targets and animation data; KTX2 addresses GPU texture storage -> do not expect a geometry codec to fix texture memory. [executive_summary[7]] [22][executive_summary[8]] [14]

## Ahujasid mcp tools assets and port 9876

### What actually runs

The project named in the question is a community integration, not an official Blender feature. Its two components are `addon.py`, running inside Blender, and `src/blender_mcp/server.py`, running outside Blender as the MCP server. The documented prerequisites are Blender 3.0+, Python 3.10+ and `uv`; the inspected README identifies version **1.5.5**. [1_ahujasid_mcp_tools_assets_and_port_9876[0]] [12]

The normal topology is:

```text
MCP client
  -> launches uvx blender-mcp using MCP stdio
  -> Python MCP process connects to localhost:9876
  -> Blender add-on receives socket commands
  -> Blender Python API changes the open scene
```

The README supplies the `uvx` client configuration and the default host/port. Port 9876 is the Blender-side socket, not a public HTTP MCP endpoint. [1_ahujasid_mcp_tools_assets_and_port_9876[0]] [12]

## Headless linux the june 2026 failure case

### Why `blender -b` and ahujasid MCP are different questions

Blender can perform background work, but that does **not** mean every Blender add-on works in background mode. Issue #251, opened **May 19, 2026**, documents commands hanging because the add-on schedules work with `bpy.app.timers` while the background process does not run the needed timer loop. The issue was closed on June 11. [2_headless_linux_the_june_2026_failure_case[0]] [8]

The decisive follow-up is **PR #272**, created **June 10, 2026** and marked merged. It does not add general background support: it refuses to start the socket server when `bpy.app.background` is true, and directs users to GUI Blender or a virtual display. The PR explains that the old behavior could appear connected while every command waited until the **180-second timeout**. [2_headless_linux_the_june_2026_failure_case[1]] [18]

This is a useful failure case: the original issue includes a proposed worker-thread workaround, but the upstream resolution is a guard against unsupported background execution. Do not present the proposed workaround as supported functionality. [2_headless_linux_the_june_2026_failure_case[0]] [8][2_headless_linux_the_june_2026_failure_case[1]] [18]

### Choose among four execution models

| Option | Execution model | Display requirement | Main trade-off |
|---|---|---|---|
| ahujasid add-on, normal use | Persistent open Blender plus socket bridge | GUI event loop | Interactive scene state; not supported with `-b`. [2_headless_linux_the_june_2026_failure_case[1]] [18] |
| ahujasid under Xvfb | GUI Blender on a virtual X display | No physical monitor; virtual display exists | Retains the supported GUI path, but still runs GUI Blender. [2_headless_linux_the_june_2026_failure_case[1]] [18] |
| sandraschi/blender-mcp | Starts headless Blender subprocesses; optional live bridge | Headless batch mode documented | Batch jobs and live viewport tools are distinct modes. [2_headless_linux_the_june_2026_failure_case[2]] [15] |
| Blender Lab MCP | Add-on/client/server architecture plus explicit `*_for_cli` tools | CLI tools open files in background Blender | Requires Blender 5.1+; not a drop-in port-9876 replacement. [2_headless_linux_the_june_2026_failure_case[3]] [13][2_headless_linux_the_june_2026_failure_case[4]] [6] |

For the original add-on on a server without a monitor, the upstream-supported direction is:


The virtual-display invocation is explicitly recommended by PR #272. You still need to install/enable the add-on and start its socket server; starting Blender alone does not activate MCP. For unattended production jobs, ordinary `blender -b --python` is the simpler recommendation. Blender Lab is worth distinguishing from similarly named community projects. Its tool list includes `execute_blender_code_for_cli` and background blend-file summary tools; the inspected tool documentation is dated **August 6, 2026**. Its public page says Blender has no built-in LLM connection and requires three external components. ### Execute-code security and data handling

Treat generated Python as having the permissions of the Blender process. Run under an unprivileged account or isolated VM/container, expose only a disposable project directory, remove cloud credentials and SSH keys, and restrict outbound network access where possible. These are deployment recommendations motivated by the explicit arbitrary-code warning, not a claim that MCP provides a sandbox. [2_headless_linux_the_june_2026_failure_case[5]] [12][2_headless_linux_the_june_2026_failure_case[3]] [13]

Keep the socket local; use an SSH tunnel rather than exposing it publicly:

```bash
ssh -N -L 9876:127.0.0.1:9876 user@render-server
```

The README also documents telemetry: with consent, prompts, code snippets and screenshots can be collected; without consent, minimal anonymous usage remains. `DISABLE_TELEMETRY=true` is the documented full-disable control. [2_headless_linux_the_june_2026_failure_case[5]] [12] Poly Haven assets are CC0 and permit commercial use and redistribution, but that does not establish licenses for Sketchfab assets or generated outputs. [2_headless_linux_the_june_2026_failure_case[6]] [23]

**Decision:** no physical display is necessary, but upstream ahujasid still needs a GUI event loop. For true no-display batch execution, select a background-oriented alternative or direct scripts.

## Blender 4 5 5 0 export a scrubbable timeline

### Use glTF's representable animation channels

Blender's versioned manuals identify three core animation categories: object location/rotation/scale, pose bones, and shape-key values. They explicitly warn that other animated properties, including physics, lights and materials, are ignored by the documented exporter. Shape keys become glTF morph targets. [3_blender_4_5_5_0_export_a_scrubbable_timeline[0]] [17][3_blender_4_5_5_0_export_a_scrubbable_timeline[1]] [11]

For a web motion-graphics hero, this suggests a concrete authoring strategy: bake constraints and procedural motion into object or bone transforms, bake appearance into supported PBR textures, and use shape keys for fixed-topology deformation. Rebuild genuinely interactive material/light changes in three.js. Do not expect Blender simulation caches, compositor effects or arbitrary procedural node behavior to become browser programs merely by exporting a GLB.

| Export mode | Blender's documented behavior | Recommended scenario |
|---|---|---|
| Actions | Exports active or NLA-stashed actions associated with objects | Separate named clips. [3_blender_4_5_5_0_export_a_scrubbable_timeline[0]] [17] |
| Active Actions merged | Ignores NLA organization and exports one animation from active actions | One coordinated hero sequence. [3_blender_4_5_5_0_export_a_scrubbable_timeline[0]] [17] |
| NLA Tracks | Exports each NLA track as an independent animation | Deliberately organized clip library. [3_blender_4_5_5_0_export_a_scrubbable_timeline[0]] [17] |
| Scene | Exports animation as seen in the viewport | A composed timeline with evaluated motion. [3_blender_4_5_5_0_export_a_scrubbable_timeline[0]] [17] |

Use **one intended timeline** for scroll scrubbing unless the page explicitly blends several clips. In the NLA workflow, put each action on its own track. Rename tracks deliberately: matching track names on different objects can merge their animation into one glTF clip. [3_blender_4_5_5_0_export_a_scrubbable_timeline[0]] [17]

### Recommended export checklist

1. Export **glTF Binary (`.glb`)** for a convenient single deployable asset. Keep a separate unoptimized master for iteration.
2. Enable animations and choose the mode intentionally; do not rely on a default that happens to work for one scene.
3. Enable shape-key geometry and shape-key animation together. Blender 5.0 also documents that sampling bone-driven shape-key drivers requires the mesh to be a direct child of the armature. [3_blender_4_5_5_0_export_a_scrubbable_timeline[1]] [11]
4. Enable animation sampling for constrained or driven movement. Use **Bake All Objects Animations** when constrained objects have no animation of their own. The 4.5 manual warns that not sampling can produce incorrect exports. [3_blender_4_5_5_0_export_a_scrubbable_timeline[0]] [17]
5. Start with sampling every frame, then optimize and compare. This is a fidelity-first recommendation, not a requirement that every project retain every sample.
6. Reopen the exported file in an independent glTF viewer and verify clip names, duration, start/end poses, morph deformation, textures and camera framing.

**Worked authoring case:** for a product hero whose lid opens while several parts separate, first create a single Blender timeline. Bake the constrained lid motion and part transforms, then export in Scene mode. For a product with discrete "open", "close" and "explode" interactions, organize named Actions/NLA tracks instead. These are implementation examples, not reported commercial case studies.

The mechanism is the distinction between **evaluated scene motion** and **stored reusable actions**. Choosing the wrong export mode can omit an action or produce multiple clips when the browser expects one. The manual's requirement that actions be active or NLA-associated is particularly important for apparently missing animations. [3_blender_4_5_5_0_export_a_scrubbable_timeline[0]] [17]

**Decision:** settle the browser's clip structure before compressing the file. Compression cannot repair omitted animation channels.

## Geometry textures and a practical hero budget

### Draco versus Meshopt: optimize the actual bottleneck

| Approach | What it targets | Browser setup | Recommended use |
|---|---|---|---|
| Draco | Mesh geometry | Configure a Draco decoder on GLTFLoader | A valid option when geometry transfer dominates; compare output and decode behavior on target devices. |
| Meshopt | Geometry, morph targets and animation data | `GLTFLoader.setMeshoptDecoder(...)` | Particularly relevant to animated GLBs; it is not a texture compressor. [4_geometry_textures_and_a_practical_hero_budget[0]] [22] |
| WebP textures | Image transfer size | Supported glTF image-extension path | Useful for compact delivery, but not GPU-compressed texture storage. [4_geometry_textures_and_a_practical_hero_budget[1]] [14] |
| KTX2/Basis textures | Texture delivery and GPU storage | KTX2Loader plus Basis transcoder | Prefer when GPU texture memory/upload is the limiting factor. [4_geometry_textures_and_a_practical_hero_budget[1]] [14] |

Draco is not "better" or "worse" in the abstract. Keep an uncompressed master and compare the compressed variants for visual error, transferred bytes, decode cost and animation correctness. glTF Transform itself warns that the all-in-one optimizer's defaults are not ideal for every scene. [4_geometry_textures_and_a_practical_hero_budget[2]] [21]

Concrete command recipes:

```bash
npm install --global @gltf-transform/cli
gltf-transform inspect raw.glb

# Documented all-in-one geometry + image-delivery path:
gltf-transform optimize raw.glb hero-draco-webp.glb   --compress draco --texture-compress webp

# Alternative geometry/animation path:
gltf-transform meshopt raw.glb hero-meshopt.glb

# Alternative texture encodings; install the encoder tooling required
# by your CLI version, then check the command help for tuning options.
gltf-transform uastc hero-meshopt.glb hero-meshopt-uastc.glb
gltf-transform etc1s hero-meshopt.glb hero-meshopt-etc1s.glb

gltf-transform validate hero-meshopt-uastc.glb
gltf-transform inspect hero-meshopt-uastc.glb
```

The CLI documents these commands, including inspection, validation, Meshopt, Draco, UASTC and ETC1S; the Draco/WebP optimizer command is its published example. [4_geometry_textures_and_a_practical_hero_budget[2]] [21]

### A concrete texture case: small download is not small memory

A **2026 Khronos presentation** gives the following example. These are that example's numbers, not compression ratios guaranteed for every texture. [4_geometry_textures_and_a_practical_hero_budget[1]] [14]

| Texture encoding | On disk, as reported | In memory, as reported |
|---|---:|---:|
| JPEG quality 75 | 0.41 MB | 21.33 MB |
| WebP quality 75 | 0.14 MB | 21.33 MB |
| KTX2 UASTC | 4.00 MB | 4.00 MB |
| KTX2 ETC1S | 0.31 MB | 4.00 MB |

WebP wins transfer size in this example, while KTX2 reduces texture memory. UASTC is not automatically the smallest download; texture type and visual quality must drive the choice. [4_geometry_textures_and_a_practical_hero_budget[1]] [14]

The same presentation recommends WebP for delivery and KTX2 for multi-asset use, and identifies UASTC as useful for configurators/geospatial workloads. That tension matters: **one hero asset and a large configurator need not use the same texture strategy**. [4_geometry_textures_and_a_practical_hero_budget[1]] [14]

### Suggested launch budgets, not a universal standard

Use these as initial engineering targets, not claimed industry averages:

| First-load hero payload | Proposed target | Decision |
|---|---:|---|
| Mobile-first | 1-3 MB | Favor simple geometry, 1K textures and a poster fallback. |
| Desktop-focused | 3-5 MB | Spend extra bytes only where the camera reveals detail. |
| Deliberate heavy experience | 5-10 MB | Defer loading and validate on slower devices/connections. |

Count the GLB, external textures and environment map; measure JavaScript and decoders separately in the complete page budget. As a simple transfer-only calculation, **3 MB at 10 Mb/s takes 2.4 seconds**, before latency, decoding and GPU upload. Threedium's separate reference of 30 meshes/80,000 polygons/1K textures is useful for complexity, but does not establish a universal MB limit. [4_geometry_textures_and_a_practical_hero_budget[3]] [3]

**Decision:** profile bytes, draw calls, animation work and GPU texture memory independently. A tiny compressed GLB can still be expensive to render.

`hero.js`:

```javascript
import * as THREE from 'three';
import { GLTFLoader } from 'three/addons/loaders/GLTFLoader.js';
import { MeshoptDecoder } from
  'three/addons/libs/meshopt_decoder.module.js';
import { KTX2Loader } from 'three/addons/loaders/KTX2Loader.js';

const renderer = new THREE.WebGLRenderer({
  canvas: document.querySelector('#hero'), antialias: true
});
renderer.setPixelRatio(Math.min(devicePixelRatio, 2));
const scene = new THREE.Scene();
scene.background = new THREE.Color(0xeeeeee);
const camera = new THREE.PerspectiveCamera(40, 1, 0.1, 100);
camera.position.set(0, 1, 5);
camera.lookAt(0, 0, 0);
scene.add(new THREE.HemisphereLight(0xffffff, 0x444444, 3));

const ktx2 = new KTX2Loader()
  .setTranscoderPath(
    'https://cdn.jsdelivr.net/npm/three@0.180.0/examples/jsm/libs/basis/'
  )
  .detectSupport(renderer);

const loader = new GLTFLoader()
  .setMeshoptDecoder(MeshoptDecoder)
  .setKTX2Loader(ktx2);

const gltf = await loader.loadAsync('/assets/hero.glb');
scene.add(gltf.scene);
const clip = gltf.animations.find(c => c.name === 'Hero')
  ?? gltf.animations[0];
if (!clip) throw new Error('GLB contains no animation clip');

const mixer = new THREE.AnimationMixer(gltf.scene);
const action = mixer.clipAction(clip);
action.setLoop(THREE.LoopOnce, 1);
action.clampWhenFinished = true;
action.play();

function resize() {
  renderer.setSize(innerWidth, innerHeight);
  camera.aspect = innerWidth / innerHeight;
  camera.updateProjectionMatrix();
}
addEventListener('resize', resize);
resize();

function render() {
  const range = Math.max(
    1, document.documentElement.scrollHeight - innerHeight
  );
  const progress = THREE.MathUtils.clamp(scrollY / range, 0, 1);

  // Re-enable after reaching the end so backward scrubbing works.
  action.enabled = true;
  action.paused = false;
  mixer.setTime(progress * clip.duration);

  renderer.render(scene, camera);
  requestAnimationFrame(render);
}
render();
```

This uses **absolute timeline seeking**, not elapsed-time playback: scroll progress chooses the time in the clip. Do not also call `mixer.update(clock.getDelta())`, because that would advance the animation independently of scrolling. The explicit action reset addresses the endpoint behavior of a clamped, non-looping action.

For a page with several sections, replace the whole-document progress calculation with progress relative to the hero's own scroll container. Fit the camera to your actual model; the camera and lighting above are placeholders. Add a poster/error fallback and reduced-motion behavior before shipping.

If your GLB uses Draco instead, configure `DRACOLoader` and call `loader.setDRACOLoader(draco)`; attaching MeshoptDecoder does not decode Draco data. Likewise, KTX2 files need their transcoder assets to remain reachable. The loader configuration is part of the asset's deployment contract. sudo ln -sfn   "/opt/blender-versions/blender-${VERSION}-linux-x64" /opt/blender
```bash
/opt/blender/blender --version

# For the 5.0.0 example, use VERSION=5.0.0 and SERIES=5.0.
```

The `sha256sum` command above computes a digest; it is **not verification until compared with the official published checksum**.

A no-display export job is:

```bash
/opt/blender/blender -b /srv/project/scene.blend   --python /srv/project/export_web.py -- /srv/output/hero.glb
```

Put the input blend file before `--python` so the script operates on that file. This is a direct batch workflow, not the unsupported ahujasid add-on background workflow discussed earlier. ### Snap is convenient, but it is a different deployment choice

The official publisher's Snap page and Blender manual document:

```bash
sudo snap install blender --classic
snap run blender -b /srv/project/scene.blend   --python /srv/project/export_web.py -- /srv/output/hero.glb
snap info blender
```

Snap automatically updates Blender, which is convenient for workstations but needs consideration for reproducible builds. Use `snap info blender` to inspect available channels rather than assuming a historical version is the current stable channel. ### Download size is not installed footprint

An exact extracted 4.5.0/5.0.0 footprint was **not established in the gathered sources**. Do not report the roughly 376-388 MB download as the installed size. Measure both logical file content and actual filesystem allocation:

```bash
# Compressed archive bytes:
stat -c '%n %s bytes' "$ARCHIVE"

# Logical file bytes stored inside the archive, without extracting:
python3 - "$ARCHIVE" <<'PY'
import sys, tarfile
with tarfile.open(sys.argv[1], 'r:xz') as archive:
    total = sum(m.size for m in archive if m.isfile())
print(total, 'regular-file bytes')
print(round(total / 1024**3, 3), 'GiB of regular-file content')
PY

# After extraction: allocation and apparent size are different measures.
du -sh "/opt/blender-versions/blender-${VERSION}-linux-x64"
du -sh --apparent-size   "/opt/blender-versions/blender-${VERSION}-linux-x64"

# Diagnose shared libraries on a minimal server:
ldd /opt/blender/blender | grep 'not found' || true
```

For initial provisioning, reserve **at least 3 GB for Blender's installation/staging area** as a conservative planning allowance, not a measured footprint. Allocate project assets, simulation caches, renders, temporary files and retained versions separately. Background mode removes the need for an interactive display; it does not promise that a minimal Ubuntu image already has every shared library or rendering driver required.

**Decision:** prefer an official, version-pinned tarball for repeatable build nodes; use Snap when automatic updates are an intentional operational choice.

## A repeatable bpy export job

The useful production boundary is a reviewed Python script: MCP may help author the scene, but the script defines what the build exports. The recipe below targets the **Scene** export mode documented in Blender 4.5 and 5.0, with morphs and sampled animation enabled. The manuals explain that Scene mode exports evaluated viewport animation and that constrained objects may need baking. [7_a_repeatable_bpy_export_job[0]] [17][7_a_repeatable_bpy_export_job[1]] [11]

Save this as `export_web.py`:

```python
import bpy
import os
import sys

args = sys.argv[sys.argv.index('--') + 1:] if '--' in sys.argv else []
if len(args) != 1:
    raise RuntimeError('Expected one output GLB path after --')
output = os.path.abspath(args[0])
os.makedirs(os.path.dirname(output), exist_ok=True)

print('Blender:', bpy.app.version_string)
print('Background:', bpy.app.background)
print('Frames:', bpy.context.scene.frame_start,
      bpy.context.scene.frame_end)

# Check the installed exporter rather than silently changing behavior
# if a different Blender/exporter version is deployed.
properties = bpy.ops.export_scene.gltf.get_rna_type().properties
options = {
    'filepath': output,
    'export_format': 'GLB',
    'export_animations': True,
    'export_animation_mode': 'SCENE',
    'export_frame_range': True,
    'export_force_sampling': True,
    'export_bake_animation': True,
    'export_morph': True,
}
missing = [key for key in options if key not in properties]
if missing:
    raise RuntimeError('Exporter options unavailable: ' + str(missing))

bpy.ops.export_scene.gltf(**options)
print('Exported:', output, os.path.getsize(output), 'bytes')
```

Run it against an existing, saved `.blend` file:

```bash
mkdir -p /srv/output
/opt/blender/blender -b /srv/project/scene.blend   --python /srv/project/export_web.py -- /srv/output/raw.glb

gltf-transform inspect /srv/output/raw.glb
gltf-transform meshopt /srv/output/raw.glb /srv/output/hero.glb
gltf-transform validate /srv/output/hero.glb
```

The preflight checks parameter availability, not whether your particular constraints, rig or procedural effect export correctly. Validate the result visually as well as structurally. glTF Transform's inspection and validation commands are documented tools for this stage. [7_a_repeatable_bpy_export_job[2]] [21]

**Worked pipeline case:** a scene authored interactively through ahujasid MCP can be saved once, exported by this background job, compressed, and loaded by the scroll-driven browser code. This separates the interactive GUI/event-loop requirement from the deployment build. The same scene does not need a live MCP server on the website or build node.

**Decision:** record the Blender version, frame range, exported clip names, raw/optimized byte counts and visual regression result in each build. That makes failures attributable to authoring, export or optimization rather than an opaque end-to-end agent session.

## Synthesis

The central distinction is between **interactive control**, **deterministic asset production**, and **browser playback**. They have different execution and trust requirements; forcing them into one always-running agent process creates unnecessary operational risk.

| Strategy | Execution/state | Display dependency | Trust boundary | Best role |
|---|---|---|---|---|
| ahujasid MCP | Persistent open scene and socket | GUI event loop, optionally virtual | Arbitrary Python in Blender | Interactive authoring. [synthesis[0]] [12][synthesis[1]] [18] |
| sandraschi MCP | Automatic headless subprocesses; optional live bridge | Batch mode does not need live bridge | Isolate script execution | Agent-driven batch automation. [synthesis[2]] [15] |
| Blender Lab MCP | Explicit CLI tools alongside interactive tools | Background CLI tools are documented | Official page still warns of unguarded generated code | Evaluate for Blender 5.1+ workflows. [synthesis[3]] [6][synthesis[4]] [13] |
| Direct bpy batch script | Saved file plus explicit script | No interactive GUI for the batch workflow | Reviewed script and input assets | Repeatable export/build jobs. [synthesis[5]] [8] |
| three.js playback | Delivered GLB plus JavaScript | Browser renderer | Client-side asset/code delivery | Runtime interaction and scroll narrative. |

The surprising tension is that **a merged headless-related fix can mean "reject headless"**, not "support headless." PR #272 is exactly that case. Conversely, a repository calling itself headless-friendly may spawn separate Blender jobs rather than preserving one interactive scene. Those are different state models, not interchangeable implementations. [synthesis[1]] [18][synthesis[2]] [15]

A second tension is transfer versus memory. The Khronos texture example shows WebP smaller on disk than either KTX2 variant, while KTX2 occupies much less texture memory. Likewise, geometry compression does not remove draw calls or convert unsupported Blender animation into supported glTF channels. [synthesis[6]] [14][synthesis[7]] [17]

My recommended architecture is therefore:

1. **Author:** Blender GUI, optionally with MCP, in an isolated working environment.
2. **Build:** a pinned Blender tarball runs a reviewed `bpy` export script in background mode.
3. **Optimize:** inspect, compress geometry and textures according to measured bottlenecks, then validate visually.
4. **Deliver:** host the asset and decoder dependencies together, pin library versions, and let scroll select animation time.

This preserves the creative convenience of MCP without making its permissions, telemetry, network connection or GUI event loop part of the production website. Start with a modest mobile payload and a fallback poster; increase complexity only when the measured experience justifies it.
