## Choose webgl or webgpu by migration cost

### Two renderer paths, not a drop-in backend switch

`WebGPURenderer` is the modern alternative to `WebGLRenderer`. Its default backend is WebGPU, with automatic WebGL 2 fallback; `forceWebGL: true` allows explicit testing of that fallback. TSL expresses shaders in JavaScript and transpiles them to WGSL or GLSL for the selected backend. [1_choose_webgl_or_webgpu_by_migration_cost[0]] [12][1_choose_webgl_or_webgpu_by_migration_cost[1]] [8]

| Path | Appropriate use | Main constraint | Recommendation |
|---|---|---|---|
| `WebGLRenderer` with GLSL | Existing marketing sites using custom shaders and `EffectComposer` | Migration is needed to use the new renderer's shader/effect architecture | Lowest migration risk for an established production pipeline |
| `WebGPURenderer` with TSL node materials | New projects designed around the node system | Async initialization; the manual still labels the renderer experimental | Adopt when its features justify testing both backends |
| `WebGPURenderer` with WebGL 2 backend | The same TSL project on devices without WebGPU | Backend fallback is not a promise that every compute-dependent feature is equivalent | Include this backend in release testing |

The critical boundary is **shader and effect compatibility**, not just browser support. Existing GLSL custom materials and `EffectComposer` passes are unsupported in `WebGPURenderer`; they must be ported. [1_choose_webgl_or_webgpu_by_migration_cost[0]] [12]

There is an important version nuance: current `WebGLRenderer` documentation also exposes a compatibility node-builder path for node materials and TSL. Therefore, "TSL can never work with WebGLRenderer" is too broad for the latest documentation. Do not assume that capability exists in an old r170 installation. [1_choose_webgl_or_webgpu_by_migration_cost[2]] [10]

For a new TSL project, the initialization pattern is:

```js
import * as THREE from 'three/webgpu';
import { color } from 'three/tsl';

const renderer = new THREE.WebGPURenderer({
  canvas,
  antialias: false,
  // forceWebGL: true, // enable in the fallback test configuration
});
await renderer.init();

const material = new THREE.MeshStandardNodeMaterial();
material.colorNode = color('#6acbff');
```

Explicit `await renderer.init()` matters when an external scheduler drives rendering. The official alternative is `renderer.setAnimationLoop()`, which ensures initialization before the first frame. Choose one scheduling owner rather than installing both. [1_choose_webgl_or_webgpu_by_migration_cost[0]] [12]

### What the published case studies actually establish

| Site and case-study date | Documented implementation | Useful lesson | Evidence boundary |
|---|---|---|---|
| **Igloo Inc., October 31, 2024** | Particle shape transitions, custom shaders, speed-linked particle color, chromatic aberration, frost/displacement transitions | Build a coherent visual language instead of layering unrelated effects | Historical precursor; its case study does not establish an `InstancedMesh` implementation or particle count |
| **J-Vers, June 11, 2025** | Scroll-responsive 3D shapes, fixed interface elements, custom shaders, Three.js and React Three Fiber | Keep orientation and reading structure stable while the scene changes | Exact pinning and text-sync code are not disclosed |
| **UntilLabs, December 10, 2025** | Approximately 60,000 particles, `GL_POINTS`, offscreen scene rendering and fullscreen shader postprocessing | Points can produce a rich swarm without one mesh per particle | Its FBO description is not, by itself, proof of FBO-based particle-state simulation |
| **Bruno's portfolio, March 11, 2026** | Instanced repeated props, culling, ETC1S/UASTC textures, DRACO, mobile quality reduction, TSL/WebGPU | High visual density requires several complementary optimizations | Interactive-world reference, not a pure scroll explainer |

Sources: Igloo [2_award_site_techniques_reproduce_the_mechanism_not_just_the_look[0]] [16]; J-Vers [2_award_site_techniques_reproduce_the_mechanism_not_just_the_look[1]] [11]; UntilLabs [2_award_site_techniques_reproduce_the_mechanism_not_just_the_look[2]] [25]; Bruno [2_award_site_techniques_reproduce_the_mechanism_not_just_the_look[3]] [15]. These sources describe techniques, not a common performance benchmark; the extracted case studies do not establish a specific award category for each site.

**Igloo's case illustrates purposeful postprocessing.** Its particles change color with speed and glow while forming shapes; chromatic aberration, frost and displacement support transitions. The team also reports custom geometry export, texture loading and shader-compilation work, rather than relying on effects alone to create the experience. [2_award_site_techniques_reproduce_the_mechanism_not_just_the_look[0]] [16]

The engineering lesson is to allocate effects to narrative moments. As a recommended starting point, use bloom on selected emissive elements, render expensive blur at reduced resolution, and animate chromatic aberration briefly during a transition rather than leaving strong color separation over text.

**UntilLabs exposes a different optimization.** Its prose describes approximately **60,000** particles, while image metadata says **65,536**; these should not be silently treated as the same precise measured count. Its documented path renders the particle scene into an FBO and then applies a fullscreen shader. [2_award_site_techniques_reproduce_the_mechanism_not_just_the_look[2]] [25]

That distinction matters: an FBO can be a scene-color intermediate, a particle-state texture, or both. Do not describe every offscreen-rendered swarm as a GPGPU simulation.

### Recommended particle implementations

| Representation | Choose it when | Code-level approach | Principal cost to watch |
|---|---|---|---|
| `THREE.Points` | Particles are small dots or sprites | One `BufferGeometry`; attributes for seed, size and target; displace in a vertex shader | Large transparent sprites and overdraw |
| `THREE.InstancedMesh` | Each particle needs actual 3D shape | Shared geometry/material; initialize instance transforms; animate using attributes and shader uniforms | Vertex count, shading and extra shadow passes |
| FBO/GPGPU simulation | Motion needs persistent velocity, forces or history | Ping-pong position/velocity textures; sample resulting positions during drawing | Simulation passes, float-target compatibility and memory |
| WebGPU compute | The effect genuinely needs compute/storage-buffer features | Use a compute-capable node pipeline and define a separate lower-capability variant | Backend portability and implementation complexity |

These are implementation recommendations, not claims that each case study uses every technique. Start with the simplest representation that communicates the idea; reserve stateful simulation for motion that actually needs history.

For an instanced swarm, avoid rewriting every instance matrix on the CPU each frame:

```js
const swarm = new THREE.InstancedMesh(geometry, material, count);
const dummy = new THREE.Object3D();

for (let i = 0; i < count; i++) {
  dummy.position.copy(initialPositions[i]);
  dummy.updateMatrix();
  swarm.setMatrixAt(i, dummy.matrix);
}
swarm.instanceMatrix.needsUpdate = true;

// Recommended shader design:
// attributes: seed, startPosition, targetPosition
// uniforms: uTime, uScroll
// position = mix(startPosition, targetPosition, easedScroll)
//          + smallNoise(seed, uTime);
```

For FBO simulation, use the conceptual sequence **read A -> write B -> swap**, never simultaneous reading and writing of the same state attachment. With a proposed **256 x 256** grid there are **65,536** state slots; double-buffered RGBA32F position and velocity textures occupy **4 MiB** of raw state storage, excluding other targets and overhead. This is a calculated design example, not a site benchmark.

Most importantly, a live simulation is not inherently reversible. For scroll scrubbing, make the major shape transformation a deterministic function of scroll progress; let time-dependent simulation provide secondary motion. That preserves understandable behavior when the visitor scrolls backward.

## Synchronize scroll camera and dom with one progress model

### ScrollTrigger for choreography; IntersectionObserver for lifecycle

| Tool | Best role | Avoid using it for |
|---|---|---|
| Native scroll plus a lightweight frame update | Simple progress mapping without smoothing or complex pinning | Rebuilding a large timeline engine unnecessarily |
| GSAP ScrollTrigger | Scrubbing, pinning, start/end measurement, coordinated DOM and scene animation | Assuming smooth scrolling is required |
| Lenis plus ScrollTrigger | Optional eased scrolling coordinated with the same animation system | A second independent Lenis RAF loop |
| IntersectionObserver | Lazy initialization, section activation, stopping offscreen rendering | Treating threshold callbacks as a continuous, frame-accurate camera timeline |
| CSS scroll-driven animation | Progressive enhancement for DOM-only effects | Assuming it automatically controls three.js scene state |

The recommended separation is **continuous progress for choreography, visibility for lifecycle**. A simple explainer may need neither Lenis nor pinning; those are design choices, not prerequisites.

ScrollTrigger links progress directly with `scrub: true`; a numeric value such as `scrub: 0.5` adds approximately **0.5 seconds** of catch-up. Numeric scrubbing can continue after scroll input stops, so updates that must follow the animated state belong on the animation update path, not only on raw scroll callbacks. [3_synchronize_scroll_camera_and_dom_with_one_progress_model[0]] [24]

**J-Vers provides the relevant design case:** scroll-reactive shapes coexist with fixed interface elements. The stable interface supplies orientation while the 3D changes, rather than forcing every piece of content to participate in camera motion. Its source does not disclose the exact synchronization code; the following is an original implementation pattern. [3_synchronize_scroll_camera_and_dom_with_one_progress_model[1]] [11]

```js
// Assumes THREE, gsap, ScrollTrigger and Lenis are imported,
// and renderer/scene/camera/path/lookPath already exist.
gsap.registerPlugin(ScrollTrigger);

const lenis = new Lenis({ autoRaf: false });
lenis.on('scroll', ScrollTrigger.update);
gsap.ticker.lagSmoothing(0);

const state = { p: 0 };
const timeline = gsap.timeline({
  scrollTrigger: {
    trigger: '.story',
    start: 'top top',
    end: () => `+=${innerHeight * 2}`, // design choice
    pin: '.story-stage',
    scrub: true,
    invalidateOnRefresh: true,
  },
});
timeline.to(state, { p: 1, duration: 1, ease: 'none' }, 0);

let inView = true;
const observer = new IntersectionObserver(([entry]) => {
  inView = entry.isIntersecting;
});
observer.observe(document.querySelector('.story'));

function tick(seconds) {
  lenis.raf(seconds * 1000);
  if (document.hidden || !inView) return;

  camera.position.copy(path.getPointAt(state.p));
  camera.lookAt(lookPath.getPointAt(state.p));
  // Update particle morph and any DOM timeline from this same p.
  renderer.render(scene, camera);
}
gsap.ticker.add(tick);

// On teardown:
// gsap.ticker.remove(tick);
// timeline.scrollTrigger.kill(); timeline.kill();
// observer.disconnect(); lenis.destroy();
```

The Lenis event/ticker wiring and milliseconds conversion follow its official integration. Do not also enable `autoRaf` or call `setAnimationLoop()` for the same render loop. For WebGPU, initialize the renderer before registering the external ticker. [3_synchronize_scroll_camera_and_dom_with_one_progress_model[2]] [23][3_synchronize_scroll_camera_and_dom_with_one_progress_model[3]] [12]

Recommended camera design uses separate position and look-target curves, with progress sampled by arc length where steady spatial speed is desired. Keep essential headings, links and explanations in semantic DOM; synchronize visual states from the same progress variable instead of separately accumulating scroll deltas.

Call **`ScrollTrigger.refresh()`** after fonts, images, responsive layout or late-mounted sections change geometry. `update()` advances current progress; it does not replace remeasurement. Pin an outer wrapper and animate its contents to keep layout responsibilities separate. [3_synchronize_scroll_camera_and_dom_with_one_progress_model[0]] [24]

Finally, treat smoothing as optional on touch. Lenis documents iframe wheel-event limitations, Safari frame-rate restrictions, and possible `syncTouch` issues below iOS 16. Its README describes Safari as capped at **60 fps**, or **30 fps** in low-power mode; treat those as library caveats, not universal promises about every future Safari configuration. [3_synchronize_scroll_camera_and_dom_with_one_progress_model[2]] [23]

The practical lesson is that "three.js is 1.31 MB" is not an adequate current loading budget. Record the exact version, minification, content encoding, transitive imports, addons, and asset transfer separately.

A no-build deployment can use an import map:

```html
<script type="importmap">
{
  "imports": {
    "three": "https://cdn.jsdelivr.net/npm/three@0.186.1/build/three.module.js",
    "three/addons/": "https://cdn.jsdelivr.net/npm/three@0.186.1/examples/jsm/"
  }

</script>
<script type="module">
  import * as THREE from 'three';
  import { GLTFLoader } from 'three/addons/loaders/GLTFLoader.js';
  // Initialize only after the page's static content is usable.
</script>
```

The three.js installation guide supports CDN/import-map deployment and warns that this route requires manual dependency management. Keep core and addons on the same exact release. [4_deliver_three_js_without_confusing_esm_with_tree_shaking[1]] [5]

**Important distinction:** `import { Mesh } from 'three'` does not tell the browser to download only the `Mesh` portion of a remote file. Import maps resolve module names; they do not perform application-level dead-code elimination. For production, my recommendation is a build pipeline that can tree-shake, minify, code-split and report compressed output; for a small no-build site, accept and measure the complete requested graph.

**Igloo's delivery case demonstrates why geometry and initialization matter too.** Its authors report custom exporters, smaller compressed volumetric data, and loading/compilation strategies during initial load and in the background. That addresses both transfer and first-use stalls; replacing an import statement alone would not reproduce those gains. [4_deliver_three_js_without_confusing_esm_with_tree_shaking[2]] [16]

Recommended loading policy:

- Render the headline, explanation and poster without waiting for the GPU bundle.
- Dynamically import the 3D feature near its first section; do not fetch it at all in a static-only experience.
- As an initial engineering target, keep essential page JS around **150 kB compressed or less**, and investigate a deferred 3D/animation payload above roughly **250-350 kB compressed**. These are proposed review thresholds, not measured three.js package sizes or universal standards.
- Prefer a small critical asset set; defer later-scene models and textures rather than downloading the entire story before the first frame.
- Measure both cold-cache loading and shader/texture initialization on an actual lower-end phone.

**Decision:** a CDN import map is a valid distribution choice, but it is not a performance optimization by itself. Choose it for simplicity only when its measured transfer, dependency management and caching behavior meet the page budget.

## Set gpu budgets around frame time and fill rate

### Proposed starting budgets, not browser limits

The following values are **recommended starting targets for an explainer**, to be tuned with device measurements. They are not published limits or promises derived from the case studies.

| Metric | Lower-power mobile starting target | Desktop starting target | Adjustment rule |
|---|---:|---:|---|
| Sustained frame pacing | Prefer stable **30 fps** over unstable 60 | Aim for **60 fps** | Frame intervals are about **33.3 ms** and **16.7 ms** respectively |
| Active draw calls | Around **50 or fewer** | Around **100 or fewer** | Count visible scene, shadows and effect passes together |
| DPR cap | Start at **1** | Start at **1.5**; allow 2 for simple scenes | Reduce resolution before losing essential content |
| Internal pixel ceiling | Roughly **1.5-2M pixels** | Roughly **3M pixels** | A ceiling prevents high-DPR screens from exploding workload |
| Particle trial size | Start around **5k-20k** | Start around **20k-65k** | Shape, shading and sprite area matter more than count alone |
| Effects | Disable heavy blur; optional reduced-resolution bloom | Add selectively after profiling | Remove effects before degrading the explanation |

The targets deliberately leave room for DOM work, input handling and browser overhead. A nominal 16.7 ms frame interval is not a 16.7 ms allowance for JavaScript alone.

**DPR is the first high-leverage control.** The official guide explains that DPR 3 requires nine times the pixels and discourages blindly passing the full device DPR into the renderer. It also recommends capping internal resolution to avoid excessive load and power consumption. [5_set_gpu_budgets_around_frame_time_and_fill_rate[0]] [13]

A calculated example makes the risk concrete: a **1920 x 1080 CSS-pixel** canvas at DPR 2 contains **8.29M physical pixels**. One RGBA8 color attachment is about **31.6 MiB**; one RGBA16F attachment is about **63.3 MiB**, before depth, additional buffers, bloom levels or driver overhead.

Use explicit drawing-buffer dimensions when you want clear pixel accounting:

```js
function resize3D(cssWidth, cssHeight, dprCap = 1.5, maxPixels = 2e6) {
  const scale = Math.min(
    window.devicePixelRatio || 1,
    dprCap,
    Math.sqrt(maxPixels / (cssWidth * cssHeight))
  );
  const w = Math.max(1, Math.round(cssWidth * scale));
  const h = Math.max(1, Math.round(cssHeight * scale));

  renderer.setPixelRatio(1); // dimensions below are physical pixels
  renderer.setSize(w, h, false); // CSS controls displayed size
  camera.aspect = cssWidth / cssHeight;
  camera.updateProjectionMatrix();
  composer?.setSize(w, h); // WebGL EffectComposer, if present
}
```

This follows the manual's preference for knowing the actual buffer dimensions rather than hiding the multiplier inside resizing behavior. For a WebGPU effect pipeline, resize its associated targets instead of using `EffectComposer`. [5_set_gpu_budgets_around_frame_time_and_fill_rate[0]] [13][5_set_gpu_budgets_around_frame_time_and_fill_rate[1]] [12]

**Bruno's mobile preset is the concrete quality-ladder case.** It disables water blur and depth of field and reduces shadow-map resolution on mobile; compressed textures, DRACO geometry and culling complement that reduction. This supports a feature ladder rather than merely shrinking the same expensive desktop scene. [5_set_gpu_budgets_around_frame_time_and_fill_rate[2]] [15]

For profiling, inspect `renderer.info.render.calls`, triangle counts, geometry/texture counts, frame-time percentiles, and GPU timings where available. With multiple renders or passes, collect totals over the whole application frame rather than reading a counter reset after one pass. These counters are diagnostic signals, not a complete GPU-memory meter.

For WebGPU postprocessing, the current guide replaces the old composer architecture with a node-composed `RenderPipeline`, can combine effects to reduce passes, and warns that default **RGBA16 half-float** MRT attachments may waste memory when their data does not need that precision. Use the API for your pinned release; older examples may differ. [5_set_gpu_budgets_around_frame_time_and_fill_rate[3]] [6]

**Decision:** establish a quality ladder before adding spectacle. Reduce render resolution, expensive postprocessing, transparent coverage and shadows first; then simplify particles and geometry if needed. Adjust from sustained measurements, not one fast initial frame.

## Use one renderer across sections and stop invisible work

### Why "about 16 contexts" is not a safe design budget

The three.js multi-scene guide says browsers limit active WebGL contexts, describes a typical limit around **8**, and notes that creating another can lose an older context. It also states that GPU resources cannot be shared across contexts, so multiple renderers duplicate initialization and shader compilation work. [6_use_one_renderer_across_sections_and_stop_invisible_work[0]] [4]

Consequently, **approximately 16 is not a portable guarantee**. Build for one context rather than testing how close a particular browser lets you get to its limit.

| Architecture | Appropriate case | Main trade-off | Recommendation |
|---|---|---|---|
| One fixed canvas behind DOM | A continuous camera/particle narrative | Layering, hit testing and page composition need care | Best default for a connected explainer |
| One renderer with viewport/scissor views | Several independent diagrams or cards | Coordinate conversion, clipping and per-view cameras | Best for multiple visible 3D sections |
| Multiple renderers/canvases | Strongly isolated applications with a demonstrated need | Context loss risk and duplicated resources | Exception, not the default marketing architecture |

The official solution is one canvas, one renderer, and separate scenes representing virtual canvases. This is directly applicable to pages with several product diagrams. [6_use_one_renderer_across_sections_and_stop_invisible_work[0]] [4]

**Case study - the multi-diagram page in the three.js manual.** The naive decision is one renderer per diagram; the resulting constraints are context limits and resources that cannot be shared. The alternative preserves separate scene organization while centralizing the GPU owner, showing that component independence does not require context independence. [6_use_one_renderer_across_sections_and_stop_invisible_work[0]] [4]

Recommended scissor-view implementation steps are:

1. Size the shared canvas and calculate its CSS-to-buffer scale.
2. Read each placeholder's bounding rectangle, batching layout reads.
3. Skip rectangles outside the canvas/viewport.
4. Convert the rectangle into drawing-buffer coordinates, including the bottom-origin Y coordinate.
5. Set `setViewport()` and `setScissor()`; enable scissor testing; update that view's camera aspect; render its scene.

When a single fixed scene is sufficient, avoid this machinery and switch scene states from story progress instead. Do not render every section merely because it exists in the DOM.

For lifecycle management, use IntersectionObserver as a visibility gate and `document.hidden` as a page-visibility gate. Skip **simulation, controls updates, postprocessing and rendering**, not just the final draw call. For an entirely static scroll state, render only when progress, size, assets or interaction changes; an idle background need not keep the GPU awake.

Pausing GPU work does not necessarily stop the scheduler. The earlier ticker example deliberately leaves Lenis active for page scrolling; when the entire feature unmounts, remove its ticker callback, kill timelines, disconnect observers, and dispose owned geometries, materials, textures and render targets. Keep shared assets alive until their final consumer is gone.

Finally, handle context loss or initialization failure by exposing the poster and keeping the DOM usable. Recovery is worthwhile, but the sales explanation should not depend on it succeeding.

**Decision:** share GPU ownership, not necessarily scene state. A single renderer is compatible with independently authored sections and usually provides the cleanest resource and failure boundary.

## Make static reduced motion and mobile modes first class

### Reduced motion should remove the trigger, not stretch the duration

Web accessibility guidance identifies vestibular effects from motion, including dizziness and blurred vision. It recommends honoring the operating-system preference and providing a user-controlled way to disable animation; even motion shorter than five seconds can warrant caution. [7_make_static_reduced_motion_and_mobile_modes_first_class[0]] [3]

**Igloo demonstrates the accessibility tension.** Its published effect vocabulary includes glitches, chromatic aberration and text scrambles, which are visually purposeful but should not become a prerequisite for reading a marketing message. The case study does not document a specific reduced-motion implementation, so its visual result should not be copied as an accessibility specification. [7_make_static_reduced_motion_and_mobile_modes_first_class[1]] [16]

A recommended enhancement gate is:

```js
const reduceMotion = matchMedia('(prefers-reduced-motion: reduce)');
let cleanup = null;

async function configureExperience() {
  cleanup?.();
  cleanup = null;
  showStaticStory(); // readable DOM + poster, always the baseline

  if (reduceMotion.matches || userChoseStaticMode()) return;

  try {
    // Implementation should abort stale setup if the mode changes.
    cleanup = await mount3DStory();
    hidePosterAfterFirstSuccessfulFrame();
  } catch (error) {
    showStaticStory(); // renderer/context/asset failure stays usable
  }
}

reduceMotion.addEventListener('change', configureExperience);
configureExperience();
```

This is a reference pattern: production code should serialize or cancel asynchronous mounting so rapid preference changes cannot leave duplicate renderers. The static path should not create Lenis smoothing, pinned scroll ranges, camera fly-throughs, particle turbulence or expensive effects only to hide them later.

| Failure or preference | Recommended experience | Content requirement |
|---|---|---|
| Reduced motion | Static diagrams, direct section changes, optional gentle transitions | Same explanatory sequence, without forced travel or parallax |
| No WebGPU | Validated WebGL 2 backend or simpler WebGL feature | Do not assume compute effects are automatically equivalent |
| No usable GPU context | Poster/image sequence and semantic HTML | No missing claims, CTA or navigation |
| Low sustained mobile performance | Lower resolution, fewer effects, simpler particles | Preserve the focal object and labels |
| Offscreen or hidden page | Suspend scene work | Resume without a large simulation jump |

The value of these modes is continuity: a visitor should receive the same proposition even when the rendering mechanism changes.

Keep decorative canvases `aria-hidden="true"`; retain headings, descriptions, links and buttons in the DOM. If a 3D control is essential, supply an equivalent keyboard-operable DOM control. Do not make canvas-drawn text the only source of pricing, product benefits or instructions.

For non-essential automatically moving content that runs more than **5 seconds** alongside other content, provide the qualifying pause/stop/hide mechanism. Accessibility guidance also warns against flashing more than **3 times per second**, subject to the applicable flash thresholds. A reduced-motion preference is not a substitute for all these requirements. [7_make_static_reduced_motion_and_mobile_modes_first_class[0]] [3]

For mobile and battery, prefer a responsive quality ladder over a desktop scene chosen by viewport width alone. Pause decorative time-based animation when the story is idle, cap pixels, avoid unnecessary touch smoothing, and retest after sustained use rather than only on a cool device. Do not assume low-power mode or thermal state has a reliable cross-browser detection signal.

**Decision:** treat the static experience as a supported product variant. Motion should improve comprehension and attention, not determine whether the page can be understood.

## Synthesis three production strategies and their trade offs

| Strategy | Mechanism and scope | Evidence base | Main trade-off | Best fit |
|---|---|---|---|---|
| **Conservative WebGL explainer** | GLSL shaders, optional `EffectComposer`, shared fixed canvas, DOM narrative | Igloo/J-Vers techniques and established renderer path | Existing effects stay usable, but later TSL migration has a cost | Teams shipping a polished site with an existing shader library |
| **TSL-first dual-backend experience** | Node materials, WebGPU preferred, tested WebGL 2 fallback | Official renderer guidance; Bruno's 2026 implementation | Better access to modern architecture, but shader/effect migration and backend testing are real work | New projects with a reason to invest in the node stack |
| **Progressively enhanced lightweight story** | Static-first content; lazy GPU section; visibility-driven rendering | Multi-scene architecture and motion-accessibility guidance | Less continuous spectacle, lower dependency on GPU success | Broad-audience, mobile-heavy marketing and conversion pages |

These strategies differ in migration cost, visual scope, failure surface and long-term maintenance, not simply visual quality. The first two can still use the third strategy's progressive-enhancement discipline. [8_synthesis_three_production_strategies_and_their_trade_offs[0]] [12][8_synthesis_three_production_strategies_and_their_trade_offs[1]] [15][8_synthesis_three_production_strategies_and_their_trade_offs[2]] [4][8_synthesis_three_production_strategies_and_their_trade_offs[3]] [3]

The most consequential tension is that **a newer GPU API does not remove pixel, asset or narrative costs**. Bruno's example combines WebGPU with culling, compression and effect reduction; it does not replace those practices. Conversely, UntilLabs demonstrates that a visually dense particle field can use points rather than individually modeled objects. [8_synthesis_three_production_strategies_and_their_trade_offs[1]] [15][8_synthesis_three_production_strategies_and_their_trade_offs[4]] [25]

A second tension is **smoothness versus determinism**. Lenis easing, numeric ScrollTrigger scrubbing and time-dependent particle physics can each add state or latency. My recommendation is one authoritative scroll-progress value for camera, major particle morphs and DOM transitions, with only small secondary effects driven by elapsed time. The documented `scrub: true` versus numeric-scrub distinction explains why layering smoothing indiscriminately can weaken synchronization. [8_synthesis_three_production_strategies_and_their_trade_offs[5]] [24]

A third tension is **component isolation versus GPU isolation**. Separate scenes and DOM sections are useful organizational boundaries; separate contexts introduce resource duplication and context-limit risk. Keep the authoring model modular while centralizing the renderer and lifecycle. [8_synthesis_three_production_strategies_and_their_trade_offs[2]] [4]

**Recommended default:** semantic HTML plus a poster; one shared `WebGLRenderer` for an established GLSL project or a deliberately tested TSL/WebGPU stack for a new one; native scrolling unless smoothing demonstrably helps; ScrollTrigger for complex choreography; IntersectionObserver for lifecycle; explicit resolution caps; and a static mode that removes both animation and artificial pinning. That architecture captures the expressive techniques in the case studies without making spectacle a prerequisite for comprehension.
