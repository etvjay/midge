# Independent Security Review: Midge Smart Contract (`FlyCoordinator`)

**Target Contract:** `FlyCoordinator` (written with `near-sdk` 5.1)  
**Document Type:** Cryptographic Systems Auditor Security Review  
**Standard:** Builder Foundry Governance / IEEE 29148 / NEAR Protocol Security Best Practices  
**Disclaimer:** This is an **independent security review**, not a formal audit, financial endorsement, or legal warranty.

---

## 1. Executive Verdict & Risk Calibration

The `FlyCoordinator` smart contract implements a sophisticated architecture for **Constrained Arbitration with Independent Recovery**, bridging hardware-isolated Trusted Execution Environments (TEEs via Intel TDX/Roost) with NEAR L1 trustless settlement. 

The implementation demonstrates a high level of cryptographic awareness. It successfully incorporates:
* Domain-separated Ed25519 message verification matching TEE-signed batches.
* Bounded release policies (enforcing whitelist constraints and epoch basis point caps).
* Non-custodial sovereign recovery paths (`hatch_out`) requiring zero operator permissions.
* Pro-rata balance deductions with exact remainder dust conservation.

However, the review identified **one (1) High-severity structural vulnerability** regarding state transitions during asynchronous promise callbacks, along with **two (2) Medium-severity findings** relating to Denial-of-Service vectors and strict epoch enforcement.

### Severity Summary Table
| Finding ID | Category | Severity | Summary |
| :--- | :--- | :--- | :--- |
| **FINDING-01** | State Machine / Asynchronous Logic | **HIGH** | `is_settling` flag reset timing in callback creates race condition on partial failure |
| **FINDING-02** | Denial of Service (Gas / State) | **MEDIUM** | `flyers` `Vec<AccountId>` linear lookups and mutations unbounded by anything other than `MAX_FLYERS_PER_SYNDICATE` |
| **FINDING-03** | State Machine Transition | **MEDIUM** | `DarkVault` epoch increment logic occurs conditionally inside `settle_batch` rather than monotonically per batch round |

## 2. Detailed Findings

### FINDING-01: Asynchronous Settlement Flag Reset Race Condition
* **Severity:** **HIGH**
* **Category:** State Machine / Async Callback Security
* **Code Location:** `settle_batch` & `on_settlement_payout`

#### Description
In `settle_batch`, the state variable `syn.is_settling` is set to `true` immediately before dispatching the multi-recipient transfer promise:
```rust
syn.is_settling = true;
// ... Promise dispatch ...
```
In the private callback `on_settlement_payout`, `syn.is_settling` is reset to `false`:
```rust
if let Some(syn) = self.syndicates.get_mut(&syndicate_id) {
    syn.is_settling = false;
    ...
    if failed_yocto > 0 {
        syn.status = SyndicateStatus::Active;
        return false;
    }
```
If a settlement batch results in a partial failure (`failed_yocto > 0`), the contract reverts the status to `Active` and clears `is_settling = false`. However, because NEAR asynchronous cross-contract calls and callbacks execute in separate transaction receipts, an attacker or concurrent transaction can interact with the syndicate state during the window between promise dispatch and callback execution, or exploit the fact that `is_settling` blocks calls like `deposit` and `hatch_out` while leaving views open. 

More critically, if `on_settlement_payout` panics or fails under gas exhaustion, `is_settling` remains permanently locked at `true`, permanently bricking the syndicate (preventing any future settlements or escape hatches due to `assert!(!syn.is_settling)` checks in `hatch_out`).

#### Remediation
1. Wrap state mutations inside a defensive pattern or ensure that callback failure paths cannot permanently brick the contract state.
2. Implement a timeout block height or recovery mechanism for `is_settling` so that if a callback fails to resolve within $N$ blocks, an administrative or permissionless cleanup function can reset `is_settling`.

### FINDING-02: Unbounded Vector Operations on `flyers` Collection
* **Severity:** **MEDIUM**
* **Category:** Gas / Computational Denial of Service
* **Code Location:** `deposit`, `hatch_out`, `compute_pro_rata_deductions`

#### Description
The `SyndicateRecord` struct tracks participating accounts via `pub flyers: Vec<AccountId>`, checked against `MAX_FLYERS_PER_SYNDICATE = 50`. Throughout the contract, vector methods such as `.contains()`, `.retain()`, and sequential iteration are performed on `syn.flyers`:
```rust
pub fn has_member(&self, account_id: &AccountId) -> bool {
    self.owner == *account_id || self.flyers.contains(account_id)
}
```
While 50 elements is small, `Vec<AccountId>` stored inside an `IterableMap<String, SyndicateRecord>` means that *every* deposit, hatch-out, and settlement batch deserializes and serializes the entire `SyndicateRecord` borsh-encoded blob, including the vector of AccountIds. As state size grows or if syndicate scaling parameters are increased in future upgrades, this pattern introduces severe gas overhead and storage deserialization penalties (violating NEAR storage best practices for collection scaling).

#### Remediation
Migrate flyer membership tracking out of the primary `SyndicateRecord` borsh blob and rely strictly on the dedicated `escrows: LookupMap<(String, AccountId), NearToken>` structure, or use `near_sdk::store::LookupSet` for membership checks instead of linear `Vec::contains` and `Vec::retain`.

### FINDING-03: Conditional Epoch Increment in DarkVault Syndicates
* **Severity:** **MEDIUM**
* **Category:** State Machine Transition Logic
* **Code Location:** `settle_batch`

#### Description
For `DarkVault` syndicates, the epoch increments conditionally based on whether the syndicate is fully settled:
```rust
if syn.total_escrow.as_yoctonear() == 0 {
    syn.status = SyndicateStatus::Settled;
} else if syn.syndicate_type == SyndicateType::DarkVault {
    syn.epoch += 1;
    syn.epoch_start_block = env::block_height();
    let next_seed = format!("{}:{}:{}", syn.id, syn.epoch, env::block_height());
    syn.round_nonce = hex::encode(env::sha256(next_seed.as_bytes()));
}
```
If a `DarkVault` syndicate executes multiple settlement rounds before exhausting its escrow, `syn.epoch` and `syn.round_nonce` increment correctly. However, if `total_escrow` reaches 0 precisely on a batch, the contract marks the syndicate as `SyndicateStatus::Settled` and skips the epoch increment block. If off-chain enclaves expect epochs to advance monotonically regardless of finality state, this can lead to signature verification desynchronization between the L1 contract and the Roost TEE.

#### Remediation
Ensure epoch and round nonce generation increments unconditionally per successful settlement batch, decoupling epoch progression from terminal status transitions.

## 3. Invariant Evaluation

We evaluated the `FlyCoordinator` contract against the core invariants mandated by the Midge threat model:

1. **Release Policy Bounding (Threat T1):**  
   * *Invariant:* Payouts cannot exceed `max_release_bps_per_epoch`, cannot exceed `total_escrow`, and must target addresses within `allowed_recipients`.  
   * *Evaluation:* **PASSED.** `settle_batch` rigorously asserts all three conditions prior to signature verification and promise dispatch.
2. **Sovereign Escape Hatch (Threat T2):**  
   * *Invariant:* After timeout or deadline expiration, any flyer can withdraw 100% of their escrow without operator permission or coordinator signatures.  
   * *Evaluation:* **PASSED.** `hatch_out` checks `blocks_passed >= syn.timeout_blocks` or `release_policy.is_deadline_passed`, requires no signatures, and directly transfers funds via NEAR native promises with a safe rollback handler.
3. **Nonce Replay Prevention (Threat T4):**  
   * *Invariant:* Signed messages are bound to syndicate ID, epoch, round nonce, allocations hash, and order hash.  
   * *Evaluation:* **PASSED.** `settle_batch` verifies `syn.round_nonce == attestation_nonce` and checks the full 6-tuple domain-separated Ed25519 signature.
4. **Exact Dust Conservation (Threat T5):**  
   * *Invariant:* Sum of pro-rata deductions equals `total_payout_yocto` without value creation from integer truncation.  
   * *Evaluation:* **PASSED.** `compute_pro_rata_deductions` accurately tracks `sum_deducted` and assigns fractional remainder dust to the flyer with the largest balance.

## 4. Formal Conclusion

The `FlyCoordinator` contract (near-sdk 5.1) presents a robust cryptographic architecture implementing hardware-enclave constrained arbitration with a trustless sovereign recovery hatch. The cryptographic bindings (Ed25519 verification, policy hashes, canonical allocation hashes) are implemented correctly. 

Addressing **FINDING-01** (async callback state locking) and **FINDING-02** (state deserialization efficiency) is strongly recommended before mainnet deployment to ensure high availability under adverse network conditions.
