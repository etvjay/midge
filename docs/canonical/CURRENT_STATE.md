## 1. Executive Summary

Midge is a network of private rooms with public rules on NEAR Protocol. It enables autonomous AI agents, quant funds, and privacy collectives to pool capital, deliberate in hardware-attested enclaves, and execute cross-chain operations as a unified front without leaking member identities, proprietary trading models, prompt weights, or internal equity splits to public mempools.

All 8 architectural verification layers, the NEAR L1 Rust smart contract (174 Rust tests: unit, integration, invariant and state-machine; domain-separated Ed25519 signature verification, LookupMap escrow storage, Flash Promise settlement payouts with failure-recovery callbacks, per-member charges, two-room settlement, a release cap paced by the exit timer, and a permissionless exit), the hosted Roost on a real Phala TDX machine, and the Builder Foundry governance control plane are implemented and verified in **<4.0 seconds**.

## 3. Known Limitations & Builder Foundry Gaps

1. **NEAR L1 Private Sharding (GAP-002):**
   - *Current State:* Evaluated as an in-process PBFT 200ms cryptographic state machine with IMT token accounting and decoupled graph verification.
   - *Roadmap:* Integration with native NEAR Nightshade Phase 2 validator RPC once private sharding ships.
2. **1Click Swap API Environment (GAP-001):**
   - *Current State:* 1Click API operates in a mainnet environment without dedicated public testnet; verified via live asset queries with audited snapshot fallback.
3. **Chain Signatures Testnet Signing (GAP-005, closed):**
   - *Current State:* Closed. A live `sign` transaction to `v1.signer-prod.testnet` is on testnet and the signature was verified against the derived key. Re-running it needs a funded testnet key. Since 2026-11-10 the signed transactions are also broadcast: a SOL transfer on Solana devnet (Ed25519, signer domain 1) and an ETH transfer on Sepolia (secp256k1, domain 0), as one two-payee pay run. Nothing has been sent on Bitcoin. Since 2026-11-11 the Midge contract (`c.fly-1793636729.testnet`, first proven on the test copy `m.fly-1793636729.testnet`) asks the signer itself: the Midge contract checked the group's foreign-payment rules and asked the signer for both payments, which landed on Solana devnet and Ethereum Sepolia, and it refused three out-of-rules requests (`npm run verify:contract-payroll`, `docs/canonical/contract-payroll-evidence.json`). Foreign funds are outside the NEAR escrow, so a member's exit does not reach them (a finished group can still pay its listed payees within the caps; a payee's running total is per window); the production contract was upgraded on 2026-11-11 and the promoted run `20261111T063548Z-dd0c` ran on the current build, and the room key is a test key, not the hosted Roost (GAP-045, GAP-047, GAP-048).
4. **Hardware hosting of the room (GAP-004):**
   - *Current State:* The default room is the local simulation and is not in hardware. The model-sealed Roost seals bids to a NEAR AI Cloud model's attested key. The hosted Roost has been attested on real Phala TDX machines (2026-11-04, and 2026-11-08 with the escrow check on). Those VMs were ephemeral and were deleted; **no hosted Roost is running now**.
5. **Intel DCAP-QVL Verification (GAP-006, closed):**
   - *Current State:* The Intel certificate chain to the Intel root and the TCB status are checked with `dcap-qvl`, and a machine without it now fails closed (GAP-035). An optional pin of the host's measurements (MRTD, RTMR0 to RTMR3, MRSEAM) exists (GAP-043): set `MIDGE_MODEL_MEASUREMENTS`, and read the current values with `npm run measure:model`. The library pins nothing by default, because deciding which build to trust is the owner's decision. The live model check (`scripts/verify-roost-model.js`) compares the host with a tracked baseline of what was observed on the real host (`docs/canonical/model-measurements.json`, only observed, not verified): a host that differs only in its measurements gets a warning rather than a failure, `--require-pin` makes it a failure and `--no-pin` skips the comparison; `E-MODEL-PIN-LIVE-01` showed it accepted and a wrong value refused (CLM-MODEL-PIN-01).
6. **Sybil Syndicate Capacity & Storage Staking (GAP-007):**
   - *Current State:* Fixed 50-flyer capacity cap with 0.01 NEAR minimum deposit to bound contract memory and gas costs. Storage deposit is statically allocated at hatch time.
   - *Roadmap:* Dynamic per-flyer storage deposit refundable upon hatch_out or settlement.

- MCP over HTTP: every tool outside a short public list needs the coordinator key.

## Contract changes of 2026-11-08 (deployed; the live code hash is BVcq86Wz… since 2026-11-11 (EULUXozH… before it), 854fzUj2… was live after these changes, and FMVXMpB3… is the earlier one that carried the first change below)

### The settlement follow-up names its round (GAP-028)
The follow-up step of a settlement now names the round nonce it was signed for (`on_settlement_payout_for_round`) and acts only if that is the settlement in flight, so a late follow-up of an earlier settlement with a byte-identical payload cannot finish a newer one. The original follow-up is kept for a settlement in flight at upgrade time. A read-only `get_group_phase` view reports Open, PayoutInFlight, Settled, Refunded or Unfunded. Verified on the real contract (`E-NONCE-CALLBACK-LIVE-01`, run `20261108T153206Z-a0f0`); the late-follow-up case itself is covered by the unit tests only (CLM-CONTRACT-NONCE-01). The deployed site's contract check still expects the previous hash until the site is redeployed.

### A never-funded group can be removed (GAP-030, second part)
`prune_syndicate` also removes a group that was hatched and never funded (Active, no member, no escrow, nothing in flight): its creator at once, anyone from 604,800 blocks (about seven days) after it was created. A funded or in-flight group is never removed this way. Verified on the real contract by `E-UNFUNDED-PRUNE-LIVE-01`; the path after the waiting period is covered by the unit tests only.

## Escrow-bound charged rounds (2026-11-08, audit lead 9; in the hosted image and switched on in its measured compose file)
A charged round can read what each bidder holds from two or more providers at one block and leave out bidders who cannot pay (`bindEscrow`, `deploy/roost/ESCROW-READER.md`). Tested live on testnet with a local host (run `20261108T103619Z-433a`, after a fresh review whose Critical and Important findings were fixed). It makes a rejected round **much rarer, not impossible**: a member whose exit timer has run can still leave between the read and the payout (`escrowBlock.raceFree` is an estimate of when that cannot happen, not a guarantee). A rejected signed round can be given up with `abandon` and run again; the abandoned signature stays valid on chain and the record of it is in memory only. The hosted Roost image (`cde03fef…`, built by CI from `2fbec52`) has it, and `deploy/roost/docker-compose.yml` switches it on, so the attestation covers which providers the Roost asks and which contract it reads. Verified on a real Phala TDX VM (run `20261108T124630Z-b8de`, compose hash `edd3ff37…`, now pinned in `roost.expected.json` beside the November 4 build); the VM was deleted afterwards, so none is running now.
